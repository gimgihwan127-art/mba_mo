# 2026 하반기 라인업 — 캐스트 랜딩

이미지 두 장짜리 모바일 랜딩페이지. **빌드 도구 없음.**
저장소 루트를 그대로 GitHub Pages에 올리면 동작한다.

## 어떻게 움직이나

`.cast-carousel`(세로로 긴 트랙)이 스크롤 거리를 만들고, 안쪽 `.cast-carousel__sticky`가
화면에 붙어 있다. 그 위에서 세 장면이 이어진다.

1. **팬** — 단체사진이 화면을 가득 채운 채 **좌측 끝에서 우측 끝까지** 밀린다.
2. **줌아웃** — 다 밀면 오른쪽 끝을 붙든 채 카메라가 뒤로 빠지고,
   **이미지 전체가 16:9로** 드러난다. 윗변은 화면 위에 붙어 있고,
   줄어들며 밑에 생기는 자리는 **아래 이미지가 따라 올라와 그때그때 메운다.**
   그래서 어느 순간에도 배경만 보이는 띠가 없다.
3. 그제서야 고정이 풀리고 세로로 긴 랜딩 이미지가 이어서 올라온다.

이미지의 **기준 크기는 폭 100%**, 즉 `scale(1)`이 곧 "전체가 보이는 마지막 모습"이다.
팬 구간에서는 화면 높이를 채우도록 배율을 키워 두고, 줌아웃에서 1로 되돌린다.
원본이 6054×3407(=16:9)이라 마지막 화면이 정확히 16:9가 된다.

375×812 기준 실측값 (`gap` = 메인 이미지 밑변과 아래 이미지 윗변 사이):

| 스크롤 | 배율 | 이미지 좌/우 끝 | 밑변 | gap |
|---|---|---|---|---|
| 0 | 3.85× | 0 → 1443 | 812 (꽉 참) | 0 |
| 1335 | 3.85× | −1068 → 375 | 812 (우측 끝 도달) | 0 |
| 1817 | 1.58× | — | 296 | 0 |
| 2066 | 1× | 0 → 375 | 211 (16:9 전체) | 0 |
| 9641 (맨 끝) | 1× | — | — | 0 |

문서 맨 끝에서도 아래 이미지의 밑변이 화면 밑변과 정확히 맞는다.

화면이 이미지보다 옆으로 넓으면(1440×800 등) 배율이 1로 고정돼 팬도 줌아웃도 하지 않는다.
처음부터 전체가 보이는 게 맞기 때문이다. 375 / 768 / 1440 세 폭에서 확인했다.

## 파일

```

images/

.nojekyll     GitHub Pages가 Jekyll로 처리하지 않게
```

## 손대기 전에 알아둘 것

- **속도는 `main.js` 맨 위 두 값으로만** 조절한다.
  `PACE`는 팬(1 = 손가락이 움직인 만큼 이미지가 움직임, 키우면 느긋해짐),
  `ZOOM_SCREENS`는 줌아웃에 쓸 스크롤(화면 높이의 배수).
  트랙 높이(`--track-h`)는 `measure()`가 계산해서 덮어쓰므로 CSS에서 고쳐도 소용없다.
- **`.cast-carousel__img`의 `width: 100%`를 바꾸지 말 것.**
  이게 배율 계산의 기준이다. `height:100%`나 `object-fit`으로 바꾸면
  "마지막에 전체가 보인다"는 전제가 깨진다.
- **여백을 메우는 장치는 두 개가 한 세트다.** 하나만 지우면 어긋난다.
  - `.lineup-full`의 **음수 `margin-top`** (JS가 `measure()`에서 한 번 넣는다)
    — 레이아웃째로 끌어올려 문서 높이까지 줄인다.
    `margin-bottom`으로는 스크롤 높이가 줄지 않아 문서 끝에 빈 칸이 남는다. 겪은 함정이다.
  - `--shift` 보정 (매 프레임) — 줌 도중 밑변을 따라붙게 한다.
    고정이 풀리는 순간 정확히 0이 되도록 맞춰져 있어서, 이후로는 margin 만으로 붙어 있는다.
- **`index.html`의 `width`/`height` 속성을 지우지 말 것.**
  이미지가 도착하기 전에 JS가 높이 0을 재면 배율을 1로 잡아버려서
  팬이 통째로 사라진다. 아래쪽 긴 이미지 쪽은 스크롤 길이가 튀는 것도 막아준다.
- 이미지를 교체할 때는 **같은 파일명으로 덮어쓰고 `width`/`height` 속성만** 실제 픽셀로 고친다.
  비율이 달라져도 JS가 다시 재서 트랙 높이를 맞춘다.
  다만 16:9가 아니면 마지막 화면도 그 비율이 된다.
- `prefers-reduced-motion`이 켜져 있으면 확대도 이동도 하지 않고
  곧바로 최종 모습(전체가 보이는 상태)만 보여준다.
  새 애니메이션을 넣으면 CSS 맨 아래 블록에도 무력화 규칙을 같이 적는다.

## 로컬에서 보기

```bash
python -m http.server 5500
```

python이 PATH에 없으면 node로:

```bash
npx -y serve -l 5500 .
```

주소창에 `http://localhost:5500`.
`file://`로 열어도 대부분 동작하지만 이미지 경로가 브라우저마다 달라서 서버 쪽을 권한다.

**고쳤는데 안 바뀌면 브라우저 캐시다.** `Ctrl+Shift+R`.

## 배포 (GitHub Pages)

GitHub에서 빈 저장소를 만든 뒤, 이 폴더에서:

```bash
git init -b main
```

```bash
git add . ; git commit -m "캐스트 랜딩페이지"
```

```bash
git remote add origin https://github.com/<계정>/<저장소>.git
```

```bash
git push -u origin main
```

그다음 저장소 **Settings → Pages → Source: Deploy from a branch → `main` / `(root)`**.
1~2분 뒤 `https://<계정>.github.io/<저장소>/` 에서 열린다.

### 올린 뒤 확인

- 브라우저 콘솔에 **404가 없는지** (`style.css`, `main.js`, 이미지 2장).
- 단체사진이 **좌측 끝부터** 시작하는지.
- 390 / 768 / 1440 세 폭에서 가로 스크롤이 생기지 않는지.

### 이미지 용량

`lineup-cast.png` 14MB, `lineup-full.png` 12MB — 합쳐서 26MB다.
저장소에 올라가는 건 문제없지만(파일당 100MB 제한) 모바일에서 그대로 받는다.
급해지면 WebP로 바꾸는 걸 먼저 검토할 것. 보통 1/5~1/10로 줄어든다.
